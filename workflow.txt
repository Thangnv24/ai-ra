
Thiết kế lại dự án Ontological Reasoning in Medical Knowledge Retrieval với Codex và model 9B
Kết luận ngắn trước khi đi vào chi tiết
Đúng, base mà bạn mô tả hiện tại về bản chất là một baseline không dùng LLM: nó dựa vào rule-based NER, cửa sổ ngữ cảnh để bắt assertion, local ontology lookup, cache, schema validation, rồi xuất JSON. Với Phase 1 của cuộc thi, cách này là một baseline hợp lý vì output chính thức đang xoay quanh text, position, type, assertions, candidates, và format nộp là output.zip chứa 100 file JSON; metric công khai cũng chỉ chấm theo text, assertions, candidates, chưa thấy có metric latency trong công thức tính điểm Phase 1. 
 

Nhưng nếu mục tiêu của bạn là làm nghiêm túc để tăng điểm, thì base đó chưa phải kiến trúc tối ưu. Điểm nặng nhất của Phase 1 là candidates_score với trọng số 0.4; ngoài ra, nếu đoán đúng text nhưng sai type thì khái niệm bị tính như phát sinh thêm một lỗi mới và bị 0 điểm ở cả ba metric. Vì vậy, một baseline chỉ dựa vào seed dictionary nhỏ và exact/alias match sẽ sớm bị trần điểm ở recall candidate, coverage đồng nghĩa/viết tắt, và phân biệt type trong những ca lâm sàng phức tạp. 

Hai input mẫu bạn gửi cũng cho thấy điều đó rất rõ. Mẫu thứ nhất có đồng thời tiền sử bệnh mạn, triệu chứng hiện tại, phủ định triệu chứng, sốt/hạ huyết áp trong diễn tiến, nhiều xét nghiệm có tên viết tắt như AST/ALT/WBC/TBili, mô tả hình ảnh, thủ thuật, và thuốc như levophed, propofol, phentolamine. Mẫu thứ hai lại nghiêng về bệnh sử tuyến giáp, chọc hút kim nhỏ, “kết quả tế bào học bất thường”, và các triệu chứng vùng cổ bị phủ định như khó nuốt, khó thở, khàn tiếng. Đây là các văn bản mà span extraction đúng ranh giới, bắt assertion đúng bối cảnh, và map candidate đúng ontology quan trọng hơn nhiều so với chỉ “bắt được một vài từ khóa”. 
 

Ngoài ra, dù Phase 1 đang nộp ZIP JSON, roadmap cuộc thi cho thấy Phase 2 và Phase 3 chuyển sang API endpoint trên GPU, vì vậy việc giữ một server/pipeline rõ ràng, singleton index loader, và interface dự đoán ổn định vẫn là quyết định tốt về mặt kiến trúc lâu dài. Đồng thời, BTC nêu rõ các đội top có thể bị yêu cầu nộp toàn bộ source code, dữ liệu, model weights, README cài đặt, nên repo phải tái dựng được, chứ không chỉ cần chạy ra 100 file output. 
 

Base hiện tại mạnh ở đâu và yếu ở đâu
Base hiện tại có ba điểm mạnh rất thực dụng. Thứ nhất, nó deterministic và dễ debug. Thứ hai, việc load ontology index một lần khi server hoặc batch runner khởi động là đúng tinh thần một hệ thống inference lặp lại nhiều file. Thứ ba, các luật assertion như isNegated, isFamily, isHistorical bằng trigger gần mention là rất phù hợp với định dạng output của Phase 1, nơi assertion được chấm như tập nhãn Jaccard chứ chưa đòi một lớp reasoning sâu hay giải thích tự nhiên. 

Tuy nhiên, nếu giữ nguyên triết lý đó và chỉ “đắp thêm từ điển”, hệ thống sẽ vướng các điểm yếu có tính cấu trúc. Thứ nhất là candidate recall: Phase 1 chấm nặng trường candidates, nhưng ICD-10 và RxNorm thực tế có rất nhiều alias, biến thể viết tắt, tên thương mại, tên hoạt chất, cách viết liều lượng, và mô tả tiếng Việt không nằm trong một seed dictionary nhỏ. Thứ hai là boundary quality trên text và position, trong khi điểm text dùng WER nên việc bắt span lệch một phần, nuốt thêm hoặc thiếu bớt token dễ làm hao điểm. Thứ ba là typing precision: sai TRIỆU_CHỨNG thành CHẨN_ĐOÁN, hoặc ngược lại, bị phạt rất nặng theo đúng quy chế chấm điểm. 

Một điểm quan trọng nữa: dù phần mô tả bài toán nói đến “suy luận quan hệ giữa các khái niệm”, schema và ví dụ nộp bài của Phase 1 hiện tại không có trường relation riêng trong JSON xuất ra; ví dụ chính thức chỉ gồm các concept dictionary với text, type, candidates, assertions, position. Vì vậy, việc module relation inference có sẵn nhưng chưa emit ra JSON là đúng với Phase 1, không phải thiếu sót. Nhưng nếu bạn định dùng LLM, quan hệ và cấu trúc ngữ cảnh vẫn nên được giữ ở tầng trung gian để hỗ trợ phân loại và chuẩn hóa, thay vì bỏ hẳn. 
 

Nói ngắn gọn: baseline hiện tại tốt để làm fallback, debug, và chạy khô toàn bộ luồng, nhưng không nên là kiến trúc cuối cùng nếu bạn muốn bám sát bài toán “ontological reasoning” và tận dụng model 9B. Đặc biệt, Phase 1 hiện không thấy công thức điểm công khai nào có latency, nên bạn có quyền thiết kế accuracy-first hơn baseline ban đầu, miễn là vẫn giữ inference gọn, reproducible, và không lặp gọi model một cách vô ích. 

Thiết kế nên chuyển sang đâu khi dùng LLM 9B
Nếu chuyển sang kiến trúc có LLM, mình không khuyên dùng kiểu “một ReAct agent tự do đọc văn bản xong tự gọi tool lung tung đến khi xong”. Theo tài liệu LangChain, một agent về bản chất là model gọi tools trong vòng lặp cho đến khi hoàn thành task; cách đó rất hợp cho exploratory workflows, nhưng với bài toán chấm output JSON cố định thì dễ tăng biến động, tăng số call và khó kiểm soát offset/type/candidate. LangGraph, ngược lại, được mô tả là một low-level orchestration framework cho workflow/agent stateful, long-running, có persistence, human-in-the-loop, streaming, và đặc biệt hữu ích khi bạn cần kiểm soát graph thực thi thay vì phó mặc cho vòng lặp agent tự quyết. 

Vì thế, kiến trúc hợp lý hơn là hybrid DAG: phần dễ xác định thì để rules/regex/index làm; phần khó và mơ hồ mới giao cho LLM 9B. Cụ thể, bạn nên tách ra thành các bước ổn định: tiền xử lý văn bản, sectionization, high-recall mention proposal, retrieval top-k candidates từ knowledge base, LLM reconciliation/reranking với structured output, rồi cuối cùng là validation và serialization. Cách này vừa tận dụng LLM cho phần nó mạnh nhất là disambiguation và contextual typing, vừa tránh để model “bịa mã” hay làm hỏng offset. 
 
 

Một nguyên tắc rất quan trọng là: LLM không nên là tầng đầu tiên phát minh candidate, mà nên là tầng xếp hạng và chọn trên nền retrieval cục bộ. Điều này bám sát bài toán: candidate mapping dùng chuẩn ICD-10 cho chẩn đoán và RxNorm cho thuốc; chính vì vậy, index ontology local phải là nguồn chân lý ban đầu. CDC hiện phát hành các bộ ICD-10-CM theo kỳ fiscal year, và tại thời điểm docs hiện tại có cả FY26 April 1, 2026 và FY27 October 1, 2026; RxNorm API của NLM là web service chính thức, không cần license cho phần dữ liệu RxNorm không độc quyền, và có các endpoint như tìm theo string, approximate match, related concepts, generic product, spelling suggestions. UMLS cũng là backbone hợp lý khi bạn cần mở rộng synonym/mapping, dù việc lấy dữ liệu đầy đủ thường cần quy trình license riêng. 

Nếu bạn muốn self-host model 9B cho tầng suy luận/rerank, vLLM là một lựa chọn kỹ thuật phù hợp, vì tài liệu của họ nêu rõ có OpenAI-compatible server, hỗ trợ structured outputs mặc định, trong đó bạn có thể ràng buộc đầu ra bằng json, regex, choice, hoặc grammar; họ cũng khuyến nghị dùng JSON Schema hoặc Pydantic model để ép model trả đúng schema. Đây chính xác là những gì bạn cần cho output concept list có trường cố định, thay vì để model sinh văn bản tự do. 

Kiến trúc đích nên dùng cho repo và pipeline
Kiến trúc đích mình khuyên là hai lớp tách biệt: lớp xây dựng tri thức offline và lớp inference online/batch.

Ở lớp offline, Codex nên dựng một knowledge build pipeline có trách nhiệm tải và chuẩn hóa tài nguyên: ICD-10-CM từ CDC, RxNorm từ RxNav/NLM, các corpus công khai như NCBI Disease Corpus và MedMentions làm nguồn tham khảo/augment/eval nội bộ, và một chỗ cắm sẵn cho UMLS nếu bạn có quyền dùng. NCBI Disease Corpus là một corpus đã annotate mention-level và concept-level cho disease normalization với 793 PubMed abstracts, 6,892 disease mentions, 790 disease concepts; MedMentions là tập paper biomedical annotate theo UMLS, phát hành công khai, và có subset ST21pv hướng đến information retrieval. MIMIC-IV-Note là nguồn clinical notes rất giá trị, nhưng nó là restricted-access resource: chỉ người dùng đủ điều kiện, ký DUA và hoàn tất training mới truy cập file được. Vì vậy, downloader của bạn phải phân biệt rõ giữa nguồn public tải ngay được và nguồn restricted chỉ scaffold script/chỗ đặt credential. 

Từ các nguồn đó, knowledge layer nên chuẩn hóa thành các bảng và index địa phương: concepts.parquet, aliases.parquet, relations.parquet, drug_forms.parquet, lab_aliases.jsonl, vi_synonyms.jsonl, và ít nhất một lexical index như SQLite FTS5/BM25. Nếu muốn làm tốt hơn, bạn có thể bổ sung vector index cho alias embeddings, nhưng với bài này lexical + alias engineering thường vẫn là xương sống. Điểm mấu chốt là mọi lookup bệnh/thuốc phải đi qua cùng một abstraction, để sau này có thể thay exact match bằng hybrid retrieval mà không đụng phần còn lại. 

Ở lớp inference, pipeline nên có các node theo thứ tự gần như cố định. Node đầu đọc file UTF-8, chuẩn hóa dấu cách, giữ nguyên bản gốc để tính offset. Node tiếp theo làm sectionizer và sentence splitter. Sau đó là high-recall proposer: rules cho lab×value, liều thuốc, route/frequency, cụm triệu chứng/diagnosis phổ biến, từ viết tắt y khoa song ngữ, và pattern thủ công từ input mẫu mà bạn đã thấy trong statement. Chỉ sau khi đã có mention spans, hệ thống mới truy hồi candidate ICD-10/RxNorm/UMLS top-k, rồi mới gọi LLM 9B cho những mention mơ hồ. Assertion detection nên theo kiểu hybrid: rule-first cho các trigger rõ ràng như “không ghi nhận”, “denies”, “tiền sử”, “home meds”, “bố/mẹ/father/mother”, và LLM chỉ can thiệp khi trigger đụng độ hoặc scope mơ hồ. 
 
 

Điều mình khuyên mạnh là không gọi LLM theo từng mention nếu có thể tránh. Thay vào đó, mỗi tài liệu nên gom tất cả mention proposal chưa chắc chắn thành một hoặc một vài batch, cấp cho model đúng phần văn bản liên quan cộng với top-k candidate context, rồi bắt model trả ra JSON schema chuẩn cho cả danh sách. Với vLLM, structured outputs theo JSON schema/Pydantic rất hợp với cách này. Cách làm đó giảm số lượt gọi, giảm biến động, và quan trọng nhất là giữ LLM ở vai trò “validator + disambiguator”, không phải “người chép lại toàn bộ văn bản”. 

Codex extension, skills và workflow nào nên dùng
Với repo này, Codex extension/app rất phù hợp để khởi tạo dự án, viết code, chạy command, sửa lỗi, benchmark, và tái cấu trúc nhiều file đồng thời. Theo tài liệu chính thức, Codex CLI có thể chạy cục bộ trong terminal, đọc, sửa, và chạy code trong thư mục bạn chọn; IDE extension có thể chạy song song trong IDE và cho phép delegate task lên Codex Cloud. OpenAI cũng khuyến nghị dùng AGENTS.md như một lớp hướng dẫn bền vững để mô tả layout repo, lệnh build/test/lint, quy ước kỹ thuật, constraints, và definition of done; lệnh /init của Codex có thể scaffold file này. 

Bạn nên thêm skills, nhưng theo hướng project-specific skills, không phải đi tìm một “skill chuẩn OpenAI” mơ hồ rồi hi vọng nó tự hiểu bài thi. Tài liệu Codex nói rất rõ: skills là định dạng workflow tái sử dụng; mỗi skill là một thư mục có SKILL.md, có thể kèm script, references, assets; Codex có thể đọc skills từ .agents/skills ở repo, từ user scope, admin scope, hoặc system scope; và có công cụ $skill-installer để cài curated skills cho local use. Điều hợp lý nhất với bạn là check-in ngay vào repo một vài skill như medical-data-builder, medical-inference-runner, medical-submission-validator, medical-error-analysis. 

Về workflow framework, mình khuyên chia làm hai tầng. Tầng phát triển có thể dùng Codex + skills + thậm chí LangGraph để điều phối build/test/eval. Nhưng tầng inference nộp bài nên là một pipeline graph/dag bị khóa chặt, với số node hữu hạn, không có vòng lặp agent tự do. Nếu muốn dùng LangChain/LangGraph trong code, hãy dùng nó như một harness/orchestration runtime, không phải như một “AI lập trình agentic” ở runtime dự thi. LangChain agent loop phù hợp khi model cần tự quyết gọi tool lặp đến khi xong; LangGraph phù hợp hơn khi bạn muốn persistence, state, subgraphs, observability, nhưng vẫn tự định nghĩa kiến trúc.

====================
HOW TO USE THE LLM
====================

Do not use the LLM as an unconstrained free-text generator.

Use it in these restricted roles:
- mention typing disambiguation
- assertion disambiguation when multiple triggers conflict
- ICD-10 candidate reranking from retrieved top-k
- RxNorm candidate reranking from retrieved top-k
- span boundary cleanup only if evidence is local and explicit
- optional whole-document extraction for experiments

Do NOT use the LLM to:
- invent ICD-10 codes from memory without retrieved candidates
- invent RxNorm codes without retrieval evidence
- rewrite the whole note
- produce the final JSON without validation

Make all LLM outputs structured with Pydantic/JSON schema.
If vLLM is used, add structured output support via JSON schema.
Keep the LLM backend pluggable:
- local mock backend
- vLLM OpenAI-compatible backend
- optional llama.cpp-compatible backend if easy to add
Do not hardcode a single model.

====================
LLM CALL MINIMIZATION
====================

Avoid one call per mention whenever possible.

- group ambiguous mentions per document
- pass each ambiguous mention with:

  - retrieved top-k candidates
  - allowed assertion labels
- get back a structured list in one batch call

Use caching:
- mention-level cache
- normalized-mention + context-hash cache
